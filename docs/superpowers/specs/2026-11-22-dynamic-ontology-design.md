## 1. 产品目标与成功标准

用户把一批资料放进工作台后，能够看清其中有哪些对象、对象如何关联、哪些结论有证据、哪些互相冲突，并让 AI 基于可见且已核验的知识回答问题和做分析。

本体定义可以演化：新增类型、修改属性或约束时，系统展示影响范围，保留旧版本解释能力，按明确规则迁移；资料更新触发知识更新候选，保留证据和历史。

完成首阶段的标志是：一批真实资料能够走完上述闭环，且权限、引用、版本迁移、重复导入和冲突处理可用自动化验收证明。

## 2. 首阶段应用界面

| 入口 | 用户完成的事 | 现有能力如何演进 |
|---|---|---|
| 探索 | 提问、追问、看答案及来源、切换分析范围 | 现有 AI 问答与操作入口统一为助手面板 |
| 资料 | 导入、查看解析状态、定位原文和历史版本 | 保留数据中心、文件预览和分块能力 |
| 本体 | 定义类型/属性/关系、查看草稿和发布差异 | 由现有数据模型与关联定义演进 |
| 知识 | 审核候选对象和事实、处理重复与冲突 | 复用记录与图谱视图，加入证据和审核状态 |
| 分析 | 表格、关系路径、证据对照及保存的查询 | 复用图谱、列表和驾驶舱基础组件 |
| 管理 | 权限、审计、模型配置、备份与迁移 | 保留现有管理功能 |

原项目/销售/合同应用保留；先提供兼容入口，逐步成为本体支持的业务视图。开发流水线暂不扩大，避免它与知识服务主链互相牵制。

对象详情至少包含属性、关系、事实、证据、时间线五个视图。AI 面板随当前资料或对象携带显式范围，用户能查看检索来源及执行步骤。

## 3. 本体领域契约

### 3.1 类型与版本

`Ontology` 是一个领域语义空间；每次发布生成不可变 `OntologyRevision`。修订状态为 `draft → validated → published → retired`。

类型、属性、关系具有稳定 UUID/URI；显示名、旧字段 Key 作为标签或映射。第一阶段支持类型组合及明确的类型匹配；继承、复杂推理另做范围，不能只加一个父类型字段就宣称完整推理。

属性描述：数据类型、是否必填、是否多值、枚举、单位、引用目标、可见性及说明。关系描述：源/目标类型、方向、基数、关系属性及说明。

类型声明与数据事实分开存放。文本相似度用于建议，不直接建立类型等价关系。

### 3.2 发布与演化

发布流程：

1. 编辑草稿，生成语义差异。
2. 校验引用和约束，评估涉及对象、关系及查询能力。
3. 对非兼容变更生成显式迁移计划，在副本上试跑。
4. 验证计数、字段、引用和权限后发布，并记录当前版本指针。
5. 新写入使用当前版本；旧数据按其绑定版本解释，直到完成明确迁移。

显示名称变更不改属性身份。字段 Key 变更通过属性 ID 映射；类型改变、新增必填项、删属性、收紧关系基数必须有影响说明。删除不直接擦掉历史定义。

模型版本回退不自动等于实例数据回退；实例已迁移或已产生新写入时，要使用经过验证的逆迁移或导出补偿流程。

## 4. 对象、事实与证据

### 4.1 对象身份

已有记录通过 `(source_kind, source_id)` 映射到稳定对象 ID，保留现有数字 ID 和访问路径。新对象经统一领域仓储写入，暂时复用 EntityRecord 作为实例数据的权威存储。

本体语义定义由新模块管理；现有 EntityType / FieldDefinition 是兼容投影。实施期间关闭独立直接修改投影的路径，旧接口也必须经过同一领域服务。每次本体发布与投影变更在同一事务边界内完成。

对象版本使用乐观并发控制；写入必须带读取时的版本，冲突返回当前差异，不自动覆盖别人的修改。

### 4.2 候选声明与正式知识

`Claim` 表达一条声明，可为对象属性或对象间关系，至少携带：

- 主体、谓词、对象/值及本体修订号。
- `candidate / accepted / rejected / superseded / disputed` 状态。
- 来源、抽取方法/模型与版本、置信度、核验人及时间。
- 适用范围、业务有效时间（可未知）、系统记录时间。
- 与其他声明的支持、矛盾或替代关系。

这里的置信度是抽取器或规则的判断指标，不能展示为客观真实性概率。正式知识是经过核验的声明；AI 生成的文本不会自动成为已接受事实。

经验和方法可以作为特定类型知识对象保留，但不能与事实用同一个“真假”开关粗暴处理。

### 4.3 证据定位

`Evidence` 绑定文档 ID、原文内容哈希、解析器版本、片段稳定 ID 和引用区间。PDF 有页码时保留页码；文本/Markdown 保留字符或行区间。没有可靠位置时显示片段级定位，不能捏造页码。

更换解析器或重新分块会生成新一代片段映射，已有引用继续指向旧片段/原文快照。用户可从答案逐级查看声明、证据和原文。

本体对象自身可作为业务数据来源，但必须标明来自记录及其版本；不能把记录里的文字伪装为某份文档原句。

## 5. 资料加工与知识更新

处理作业状态：`queued → parsing → extracting → reviewing → published`；可以进入 `failed / cancelled`。失败保留原因和可重试阶段。

先固定文档快照，再解析分块。抽取器使用所选本体版本，输出受结构校验的候选，不自行扩展已发布模式。遇到缺少类型或属性时，生成模式建议到草稿区。

消歧分三层：精确来源标识、配置的业务唯一键、语义相似候选。同名只产生候选，默认由人确认合并。合并必须保存别名、来源和旧 ID 跳转映射。

幂等键至少包括文档内容哈希、解析版本、抽取器版本和本体修订；重复执行不重复发布。修订后重新抽取生成新一代候选，并与旧声明做差异比较。

原资料删除使用软删除；已有声明标注来源撤回/不可用及影响范围，保留历史证据策略。正式物理清理作为单独生命周期动作，不夹带在抽取或重建索引中。

## 6. 查询与带出处回答

统一 `KnowledgeQueryService` 接收结构化查询计划，支持：类型/属性过滤、受限深度关系展开、事实有效时间和来源筛选、文档混合检索及证据聚合。

LLM 负责提议查询计划；服务端解析、校验本体版本、权限、允许的操作、最大深度、结果数量及执行预算。工具不接收任意 SQL、任意 Python 或不受限图查询。

检索顺序：

1. 在用户范围内解析问题中的概念、对象和时间条件。
2. 按权限检索对象/关系/声明，再结合 FTS5 与向量候选寻找原文证据。
3. 汇总证据，区分已核验、待核实、冲突和推导结果。
4. 生成带引用的答案，校验引用确实属于本次可见证据集。
5. 记录查询计划、所用本体版本、证据 ID 和结果状态，以便评估与回放。

没有证据时回答未知或信息不足。规则推导必须展示规则版本和输入声明；统计口径、单位和时间区间应明确。关系路径只表达有记录的关系，除非另有经过定义的因果模型，不称为因果解释。

没有配置模型时仍可导入、建模、审核和搜索；自动抽取与生成式回答明确显示未启用，不用模拟答案冒充模型输出。没有配置嵌入模型时使用关键词检索并报告降级。

## 7. AI 助手及行动边界

统一能力注册提供描述、输入输出 schema、可用本体版本、所需权限、读写类型和执行预算。

首阶段主要能力：发现本体、查对象、沿关系查询、查事实和证据、对照来源、提出抽取/合并/本体修订草稿、提交待确认发布。

所有写操作形成服务端 ChangeSet，包含发起者、作用范围、参数哈希、对象版本、本体修订、证据、过期时间和幂等键。状态：`proposed → approved → executing → succeeded / failed / conflicted / expired`；拒绝单列为 `rejected`。

确认时只提交 ChangeSet ID；后端重验操作者、权限、对象状态及版本，确认内容与执行内容必须一致。提议后对象已变更则要求重新预览。持久化幂等状态，重启和多进程不会重复执行同一行动。

审计与关键业务写入应共享事务或可靠事件机制，避免业务成功却没有对应追踪记录。AI 的工具返回内容按不可信资料处理，不能成为新的系统指令。

未来发布为 Skill / API / MCP 时复用同一能力契约和授权策略；不会因多一种入口就复制一套工具逻辑。

## 8. 模块与数据职责

建议保持模块化单体，逐步形成以下边界；路径为建议，尚未创建应用代码。

| 模块 | 负责 | 核心依赖 |
|---|---|---|
| ontology | 语义定义、修订、差异、约束、发布 | repository、policy |
| objects | 对象身份、属性、关系、对象版本 | ontology、policy |
| knowledge | 声明、证据、核验、冲突 | objects、documents |
| ingestion | 作业、解析、候选抽取、消歧建议 | knowledge、model gateway |
| query | 结构化查询、混合检索、证据聚合 | ontology、knowledge、policy |
| assistant | 会话、意图、查询计划、工具编排 | capability registry、query |
| actions | ChangeSet、确认、幂等执行和审计 | ontology、objects、policy |
| adapters | 旧接口、模型服务、未来图引擎 | 各明确领域接口 |

最小新增持久化结构：本体及修订、稳定类型/属性映射、旧记录对象绑定与版本、声明、证据、摄取作业、ChangeSet、能力定义和助手运行记录。具体表和索引在实施计划中按单一权威数据原则细化，不预先复制整个业务库。

原文由现有内容寻址存储管理；全文和向量索引均为可重建派生数据。复杂索引任务通过持久作业推进，必须显示与源版本的对应关系。

## 9. 权限与失效处理

当前模型级权限作为兼容输入；新增语义空间、对象类型与知识证据授权。资料证据从来源继承可见性，人工派生事实可见性不能无条件放宽。

关系可见性必须满足端点和关系策略；聚合统计、摘要、引用标题同样执行约束。查询缓存必须绑定用户/权限版本、数据版本及本体修订，角色变更后失效。

一条声明由多个来源支持时分别保留证据授权；具体回答只能使用当前用户可见的证据，不能借可见来源展示另一份受限来源的内容。

明确错误：模型未配置、资料解析失败、缺少来源、模式不兼容、版本冲突、权限不足、检索降级。每类错误保留可追踪 ID，避免静默吞掉后返回貌似完整的成功结果。

## 10. 迁移和验收策略

实施从独立工作区及备份副本开始；前后端使用独立容器名、端口、文件路径与配置，绝不挂载正在运行的原始业务数据进行测试。

迁移采用显式版本脚本，保留现有类型、字段、记录、关系及附件映射。第一次只建立基线，不编造历史；不满足新约束的旧数据生成待处理报告，而非删除或悄悄强制转换。

验收矩阵：

| 场景 | 必须观察到的结果 |
|---|---|
| 新增可选属性 | 新旧对象都可读，已发布旧修订不可变 |
| 属性改名 | 值保留、引用保留、历史仍能解释 |
| 类型改动/新增必填 | 显示影响数据及迁移结果，未处理冲突不得发布 |
| 无效字段与关系基数 | UI、API、AI、CSV 导入一致拒绝，并发也不能绕过 |
| 文档导入及重复执行 | 可见候选和证据；重复发布不产生重复知识 |
| 同名不同对象 | 只提出合并候选，不自动覆盖 |
| 两份资料互相矛盾 | 保留双方来源、状态和适用时间，回答说明分歧 |
| 文档重新分块 | 已有引用仍可定位旧版本 |
| 受限用户提问 | 回答、轨迹、摘要、图谱和统计都不泄露受限信息 |
| AI 确认后对象已修改 | 返回冲突，重新预览后再确认 |
| 重复确认或进程重启 | 同一 ChangeSet 最多产生一次业务效果 |
| 模型/向量服务不可用 | 核心资料与本体功能可用，明确报告能力降级 |
| 恢复演练 | 源码、配置、数据库、全部原文引用与服务行为通过验证 |

使用经授权的一批真实样例，加上权限、矛盾、重复、改名与并发的合成资料构成评估集；测试中的模型结果使用固定契约与可回放输入。生产模型效果另做真实调用评估，不与单元测试混为一谈。

## 11. 分批交付顺序

1. M1：修复权限/约束、建立本体版本与兼容写入路径。
2. M2：资料快照、候选抽取、事实证据和核验工作流。
3. M3：统一查询、引用回答与基于 ChangeSet 的助手。

每批都有独立可运行成果和回滚方式。完整首阶段需 M1–M3；不会仅增加一个本体编辑页或调整 AI 提示词就宣告完成。

## 12. 设计评审要点

待确认的是整体方向：保留原技术栈和数据，以版本化本体内核为基础，先打通已选的资料到知识服务闭环；AI 抽取默认进入候选审核，重要写入以服务端变更计划确认。

批准本草案后，制定逐文件实施计划，再开始业务代码改动。实际 OntoFlow 产品接入、自动无审核发布、通用推演、实时流式计算和更换数据库，均需要另行明确范围和验收条件。
