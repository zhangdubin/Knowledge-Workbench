# 中文知识服务应用：基于本体基座的设计提案

日期：2026-11-22。状态：用户已批准按推荐顺序实施第一期中文知识服务（2026-11-22）。用户已明确首批场景为知识服务。当前 1.11.0 本体基座继续完成既定交付。

调研及逐项能力对照：[Palantir 知识服务适配研究](../../research/palantir-knowledge-service.md)。

## 1. 本期目标与范围

让普通业务用户直接完成中文知识查阅、版本核对、原文追溯和疑问反馈；让知识编辑者使用现有本体、候选和审核能力准备可用资料。本期交付一个具体应用，后续独立交付知识运营工作流及通用接口引擎。

首期以制度流程、保障参考资料、培训材料和项目知识为可配置领域。以实际获准资料和真实岗位问题建立验收集。普通用户无需掌握本体 UUID、JSON 或数据库结构。

本期包含：知识服务工作区、资料/知识详情、中文术语与别名筛选、适用范围与时点、受控检索、证据答复、反馈留痕和可回放评估。通用函数编程、外部 Webhook、地图、调度、仿真和跨系统联动分别立项。

## 2. 用户与完整流程

| 角色 | 完成的工作 | 操作边界 |
| --- | --- | --- |
| 查阅者 | 提问、筛选、核对出处、查看历史适用版本、提交反馈 | 只能读取当前授权范围内的资料及知识，反馈不直接改正式知识 |
| 知识编辑者 | 选择授权资料、维护词表和知识草稿、提交审核 | 复用已有候选与审核能力，业务发布流程在后续知识运营阶段独立加强 |
| 专家审核者 | 对照证据、处理现有候选、确认可用知识 | 审核、替代与撤回遵循版本和来源授权，保留人工决定 |
| 本体构建者 | 安装或调整知识服务模板、字段和关系 | 使用高级本体工作室，模式变更按预览和确认生效 |

查阅流程：选范围/时点 → 输入中文问题或文号 → 检索可见知识与原文 → 展示答案状态、适用期及引文 → 打开对应原文版本 → 有疑问时提交反馈并收到记录编号。

查阅到未审核、已过期、矛盾或缺少证据的内容时，分别显示状态与原因。适用范围不同的条款不自动判为冲突；时间较新的资料也不自动取得替代权威。

## 3. 应用入口和中文交互

- 在业务应用中增加“知识服务”，使用现有五项主导航；首页询问入口可以携带明确知识范围进入该应用。
- 主界面由问题输入、范围/日期筛选、结果与证据组成；常用任务包括查制度、查手册、看差异、追出处、提疑问。
- 知识详情展示摘要、适用范围、来源修订、相关术语、引用关系和历史。技术标识只在高级追溯区域显示。
- 界面名称、错误、空状态、状态和操作说明均以中文为主；内部稳定标识、API 枚举和外部标准名按合同保持。
- 使用现有样式和响应式布局。键盘可完成筛选、打开证据和反馈；暗色和手机布局执行真实浏览器验收。

## 4. 知识模型与数据职责

通过明确的“创建知识服务模板”动作建立领域模型，安装前展示将创建的类型、字段和关系。不在启动时自动把旧笔记或业务记录解释成新模型。

| 模型 | 业务含义 | 权威存储与要点 |
| --- | --- | --- |
| 知识条目 | 可复用说明、标准问答或经验 | 复用受管 EntityRecord、稳定字段 ID、版本和历史；依据由声明及证据关联 |
| 资料修订 | 同一规范或手册的明确版本及适用期 | 引用既有 Document、内容哈希及 SourceSnapshot；新增修订元数据，不复制原文文件 |
| 术语概念 | 中文首选词、别名、缩写、释义及领域 | 复用受管对象和关系，先实现明确的词表合同；共享属性/接口引擎后续独立建设 |
| 查询运行 | 一次范围明确的检索和答复 | 记录主体、范围、时点、本体修订、模型/提示版本、引用证据 ID、状态及预算；不保存隐式推理过程 |
| 问题反馈 | 用户对查阅结果提出的疑问 | 新增持久化反馈记录，关联查询或知识版本、问题分类、处理状态和操作者 |

关系至少包括“引用依据”“属于业务主题”“术语相关”“明确替代”。输入数据、抽取候选、专家决定和最终对外知识分开表达。原始资料和业务记录仍是各自权威来源。

Document 当前没有通用版本链或业务扩展元数据结构，不能仅用文件标题推断同一资料及替代关系。新增资料修订元数据必须引用原 Document ID、哈希和明确分组，业务生效日期与系统记录时间分别保存。

## 5. 服务边界与权限

复用 Vue、FastAPI、SQLite 和现有本体领域，新增聚焦的 knowledge_service 应用模块。保留当前模型、原文、证据、查询和变更计划作为底座。

知识应用读权限与高级工作室的 types 页面权限分开：普通读者可以获准使用知识服务而无权进入模型编辑。领域服务按明确能力授权，公开路由分别执行页面/功能和模型/来源授权；不能通过构造提升后的 Principal 复用工作室接口。

建议应用接口前缀 `/api/knowledge-service`：

- `GET /catalog`：返回当前用户可见的知识空间、资料类型、主题和范围。
- `POST /query`：接收问题、空间/类型、范围、as_of、筛选和 limit；返回状态、可见知识、引用、版本、冲突/不足原因及运行 ID。
- `GET /items/{record_id}`：返回用户获准读取的知识详情及权限过滤后的关联资料、事实、证据和时间线。
- `GET /sources/{revision_id}`：返回资料修订和可访问原文入口，页码只在可靠解析时提供。
- `GET /terms`：按授权领域查词表、别名和歧义候选。
- `POST /feedback`：持久保存对具体运行或知识版本的反馈；同一客户端幂等键重试不会重复建单。
- `GET /feedback` 与 `GET /feedback/{id}`：本人查看自己的反馈，获准审核者查看职责范围内反馈；再次校验所关联运行、知识及来源权限。
- `POST /feedback/{id}/resolve`：获准审核者提交处理说明和 expected_version，更新反馈状态并在同一事务留痕；重复提交保持幂等，过期版本返回冲突。
- `GET /runs/{run_id}`：仅允许本人或具有相应审核授权的角色读取可重放执行摘要，引用内容仍按当前来源权限重验。

首期继承最多 50 项结果、最多两跳关系和明确扫描预算。原文、答案、下拉、摘要、关系、聚合和导出执行相同授权。完整导入对象继续要求全部来源可读；字段级可见视图独立设计。

## 6. 中文检索与证据答复

1. 规范化文号、日期和中文标点，结合授权词表的首选词与别名解析问题。含义不明确时让用户选择业务范围。
2. 先限定用户可见范围及有效时点，再执行关键词/结构化检索；有模型配置时在授权集合内组合向量检索与重排。
3. 对多资料问题辅助使用已接受、可见关系及原文证据。来自候选或已拒绝关系的路径不会成为已核实依据。
4. 生成答复时只使用本次可见证据集合；服务端校验引用 ID 和原文区间。引用到不可访问、过期或集合外证据时返回可操作错误或信息不足。
5. 返回“有依据 / 存在冲突 / 信息不足 / 结果不完整”，附适用范围、时间、出处和追溯入口。模型未配置时仍可搜索并查看结构化结果，明确显示生成式答复未启用。

GraphRAG 的局部实体检索可逐步增强跨资料关联；全局社区摘要须在固定中文评测集证明收益后启用。任何派生摘要和缓存都绑定主体授权、资料版本及本体修订，上游撤回后失效。

## 7. 反馈、审核和后续知识运营

首期反馈分类：引用不正确、版本不适用、回答不完整、存在分歧、希望补充资料。反馈保存所针对的运行/条目版本，状态为待处理或已处理，允许审核者记录处理结论，不直接改写正式事实。提交时校验运行属于当前用户或其明确可读范围，不能通过伪造 ID 关联其他人的运行。

后续独立知识运营阶段提供版本化业务操作：提交复核、批准发布、退回并说明理由、替代资料、撤回知识、解决反馈。受保护工作流字段必须在统一领域写入路径校验，旧编辑器、导入与 AI 均不能通过直接改 status 绕过审核。

同一阶段再引入资料更新事件、受影响知识清单和待复核任务。通知先采用事务提交后的站内事件及去重键，外部通知按实际接收方和接口授权另行建设。

## 8. 验收及真实工作评价

建立至少 40 个共同确认的中文用例：12 个直接查阅、8 个跨资料/冲突、6 个历史适用版本、6 个跨角色权限、4 个证据不足、4 个更新影响或反馈留痕。该数量是拟定的验收集规模，不是当前模型效果的声明。

硬门槛：引用必须属于本次授权检索集合且逐字定位正确；越权、撤回、版本冲突、重复提交和未配置模型用例全部通过；反馈重试只产生一条记录；没有证据的用例不能生成有依据结论。

模型效果用专家标注的实际资料问题单独评估，报告答复正确性、引用正确性、检索召回、拒答表现和冲突识别。记录 P50/P95、每问 token/耗时及预算耗尽率，再按内网模型能力确定可接受阈值。自动化测试使用受控响应和无生产挂载的一次性数据库，不自动向外部模型发送业务资料。

业务验收至少走通两条真实任务：一个岗位查到当前适用依据并定位原文；一个岗位发现问题、提交反馈、由有权限人员查看处理记录。测试同时包括无高级工作室权限的普通读者。

## 9. 实施顺序与设计决策

推荐顺序：明确验收资料和权限矩阵 → 安装模板及版本元数据 → 知识读服务 → 中文工作区 → 受控答复与引用校验 → 反馈与评估 → 副本验收及升级。每步均有可复现用例。

采用模块化单体增量扩展。SKOS 贡献术语组织机制，SHACL 贡献约束/验证报告思想，PROV-O 和 OpenLineage 贡献来源与执行血缘，GraphRAG 贡献受控图检索方法。标准交换、通用共享接口、通用低代码规则与其他专业应用按独立阶段评估。

设计评审后再编制逐文件实施计划；本提案不改变已经批准的 1.11.0 发布范围。
