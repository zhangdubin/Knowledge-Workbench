# 📘 知识库协同记录手册（KB Workbench · v1.4）

> 本手册是 **DSH agent / 人 / 系统** 往「知识工作台（KB Workbench）」里写记录的**唯一约定**。
> 对标 vault 侧的《V-MAX Agent 协同记录手册》与《笔记 UI 排版规范》，
> 但**通道不同**：vault 走 Obsidian + MCP + 文件系统；知识库走 **Web UI / REST API / Agent 工具**，
> 数据落在 `data/kb.db` 与 `files/`，**不允许**手工改库。
>
> 任何 agent 在写笔记、改笔记、批量导入之前，先读 §0 与 §10 的硬约束，再动手。

## 0. 一页速查

| 项 | 值 |
|---|---|
| 前端 | `http://<host>:8082`（nginx，反代 `/api` 到后端） |
| 后端 API | `http://<host>:8001/api`，交互文档 `/api/docs` |
| 默认账号 | `admin`，口令取环境变量 `KB_ADMIN_PASSWORD`，**首登强制改密** |
| 会话 | HttpOnly Cookie `kb_session`（登录 `POST /api/auth/login`） |
| 数据 | `data/kb.db`（元数据 + 全文 + 向量索引）、`files/`（原文，内容寻址） |
| 备份 | `./scripts/backup.sh`，目录由 `KB_BACKUP_DIR` 指定，保留 `BACKUP_KEEP` 份 |
| 版本号 | 唯一事实来源 `backend/app/config.py` 的 `app_version`（当前 1.10.0） |
| 发布记录 | `CHANGELOG.md` 顶部一节 |
| 笔记模型 | `entity_type key = note`，字段 `title` / `content` / `tags` / `parent`（+ `data.group_id`） |
| 排版引擎 | `backend/app/services/note_format.py`（规范 v1.8 落地） |
| 笔记类型骨架 | `backend/app/services/note_profile.py`（4 类） |
| 验收 | `scripts/verify-note-format.py`(134) · `scripts/verify-note-autofmt-api.py`(24) · `scripts/kb-verify-note-autofmt.cjs`(22) · `frontend: npm test` · 后端 `unittest`(53) |

**给 agent 的十行速约定**

```text
1. 先读后写：写之前 GET 一次目标记录，确认不是覆盖别人的内容
2. 新笔记先套类型骨架，再排版；不要手拼 front-matter
3. 已有笔记只补缺：用户写的摘要 / 元信息 / 相关，一律不动
4. 凭证走 secret-toggle；代码块里保留明文（否则命令跑不了）
5. 敏感内容必须标 sensitivity，不能靠"我觉得不敏感"
6. 只走 API，不直接 UPDATE kb.db；排查用容器内只读连接
7. 删除 = 软删除（回收站），不物理删
8. 批量 > 20 条先出计划，等人点头
9. 排版必须幂等：同一篇排两次结果一字不差
10. 说"通过"必须给脚本名 + 断言数，不许凭感觉
```

## 1. 适用范围与角色

### 1.1 适用对象

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **人（vault owner / 值班）** | 一切；最终裁决 | — |
| **DSH 主 agent** | 建笔记、改笔记、批量导入、跑验收、看审计 | 改库结构、改权限、删用户 |
| **subagent** | 在派发范围内写指定笔记 | 跨范围写、批量删、改配置 |
| **AI 助理（应用内）** | 查数据、记一笔、改记录（写前出待确认清单） | 未经确认直接写 |
| **系统任务**（维护/备份/索引） | 备份、索引重建、日志轮转 | 改业务数据 |

### 1.2 制度的四个目标

1. **可追溯**：谁、什么时候、通过什么通道、改了什么（审计 + 变更日志）。
2. **可复现**：同样输入 → 同样笔记（排版幂等）。
3. **不越权**：权限点先过，敏感级别先判。
4. **可验收**：每条硬约束都能被一条脚本或一个接口证明。

## 2. 五条基本原则

| 原则 | 含义 | 违反的典型后果 |
|---|---|---|
| **先读后写** | 写之前先 `GET`；确认目标存在、内容归属、是否已有人写过 | 覆盖用户手写内容（不可逆） |
| **最小改动** | 只改需要改的字段；能追加就不替换 | 一次"整理"把原意改没 |
| **幂等** | 同一操作重复执行结果一致 | 每存一次多一坨生成块 |
| **可回滚** | 破坏性动作先备份 / 软删除 / 留旧值 | 误删无法恢复 |
| **可追溯** | 写操作要有审计与变更记录 | 出问题定位不到人 |

## 3. 访问通道与选择

| 场景 | 通道 | 说明 |
|---|---|---|
| 人日常记录 | **Web UI**（`/notes`） | 新建条自带「类型 + 自动排版」 |
| agent 写单篇 | **REST API** | `POST /api/records/type/{type_id}` + `POST /api/notes/{id}/format` |
| agent 批量导入 | **REST API + 循环脚本** | 每篇都走同一条排版流水线；> 20 篇先出计划 |
| agent 查上下文 | **REST API**：`/api/search`、`/api/documents/search`、`/api/notes/{id}/backlinks` | 混合检索（关键词 + 向量） |
| 应用内 AI | **Agent 工具**（`services/agent.py`） | 写操作先出「待确认清单」，确认后执行 |
| 排障 / 看统计 | **只读 SQL**（容器内 `docker exec kb-backend python` 打开 `data/kb.db`） | 绝不在宿主机另开连接（WAL/-shm 会打架） |

> [!danger] 禁止
> - 直接 `UPDATE` / `DELETE` `data/kb.db`（绕过审计、绕过双链、绕过 FTS/向量索引）
> - 手工编辑 `files/` 下的原文（内容寻址，改一个字节就与库里 sha 对不上）
> - 用宿主机 sqlite 连接读写正在被容器使用的库

## 4. 写入决策树：这条信息该记在哪？

```text
这条信息是什么？
│
├─ 一次性的事实 / 结论 / 踩坑 / 复盘 ──────────→ 笔记（note）
│   ├─ 有明确攻击面/复现步骤 → 类型=⚔️ 渗透/复现记录（sensitivity 默认 secret）
│   ├─ 有现象/根因/修复       → 类型=🧯 排障记录（confidential）
│   ├─ 有步骤/前置条件/验证   → 类型=📖 教程/手册（public）
│   └─ 其它随手记             → 类型=📌 通用笔记
│
├─ 结构化、要统计、要筛选的数据 ───────────────→ 业务模型记录（客户/合同/项目/费用…）
│
├─ 原始资料（PDF/日志/源码/截图） ─────────────→ 文件库（上传 → 内容寻址）+ 养料 DNA
│
└─ 会话流水（一次会话干了什么） ───────────────→ 笔记，scope=log
```

**边界规则**

- 一篇笔记只讲一件事；超过 3 个不相干主题就拆。
- 「笔记里贴一段业务数据」可以，但**统计口径以业务模型为准**。
- 原始资料不要塞进 `content`（会把库撑大、搜索变慢），走文件库 + 在笔记里双链。

## 5. 笔记数据契约

### 5.1 记录字段（JSON）

| 字段 | 类型 | 必填 | 约定 |
|---|---|---|---|
| `title` | text | 是 | 笔记名，**建议 ≤ 40 字**；不要塞整段结论（页面标题最多两行，超出截断） |
| `content` | textarea | 是 | Markdown 正文，**front-matter 存在正文开头** |
| `tags` | multiselect | 是 | 3–6 个；`#` 前缀由渲染层加，不要写进值里 |
| `parent` | reference(note) | 否 | 父笔记，用于树状结构 |
| `data.group_id` | int | 否 | 分组归属；**缺键或 0 = 未分组**（分组是标签，不是容器） |

> 笔记的「属性表」是 `content` 开头的 YAML，不是独立字段 —— 所以**不要**在正文里再写一遍同样的元信息。

### 5.2 front-matter 契约

```yaml
---
title: <与 H1 一致的人类可读标题>
tags: [a, b, c]
created: 2026-11-08          # 实际日期，禁止 = date(today) 这类表达式
updated: 2026-11-08
source: human | agent | hybrid
version: 1.0                 # 笔记内容版本，不是应用版本
scope: process | log | tutorial | concept | project | pentest-record | troubleshoot
status: draft | active | deprecated | archived
sensitivity: public | confidential | secret
related:
  - "[[另一篇笔记]]"
---
```

**三条高频踩坑（规范原文 + 代码已强制）**

1. `related` 必须是 **列表 + 引号**；`related: [[A]] | [[B]]` 会让整段 YAML 解析失败。
2. 日期写**实际值**；Templater 表达式只在写入瞬间求值，Dataview 查不到。
3. 标签不要写成 `#30456b` 这种色值 —— 排版器会清洗，但源头别产生。

### 5.3 content 结构

```text
front-matter
# <H1：带语义 emoji，可由 title 截断>
> [!danger|warning] 敏感度横幅（secret / confidential 才有）
> [!abstract] 摘要（TL;DR：一句结论 + 覆盖小节）
> [!info] 元信息（日期 · 来源/类型/状态/敏感度/版本 · 目标 · 标签 · 关联）
## 📑 目录（正文 > 40 行或 ≥ 4 节时）
--- 
## <emoji> 1. 章节
### 1.1 子节
--- 
## 🔗 相关
## 📝 变更日志
```

## 6. 排版制度（规范 → 实现的映射）

> 规范来源：`vault/topics/methodology/笔记UI排版规范.md`（v1.7）。
> 本站实现：`services/note_format.py`（规则层，v1.8）+ `services/note_profile.py`（骨架）+ `services/ai.structure_note`（AI 结构化，可选）。

### 6.1 谁来排

| 入口 | 调用 | 是否落库 |
|---|---|---|
| 新建笔记（自动排版开关，默认开） | `POST /api/notes/format` → 再建记录 | 是（先预览式排版后入库） |
| 套用类型模板 | `POST /api/notes/template`（profile） | 只回文本，用户再保存 |
| 已有笔记「排版」 | `POST /api/notes/{id}/format` | 是（顺带重算双链） |
| 弹窗预览 | `POST /api/notes/format` | 否（只给 text / changes / elements） |

### 6.2 规则覆盖（都能在验收脚本里找到断言）

| 规范 | 实现 |
|---|---|
| §1 标题层级 | H1 按身份配 emoji（渗透 ⚔️ / 排障 🧯 / 教程 📖）；H2 按语义配；全文只留一个 H1；**章节自动编号 1. / 1.1** |
| §2 front-matter | 合并补齐（已有值不覆盖）；`related` 规范化 + YAML 自检；日期表达式落成实际值 |
| §3 callout | 引用转 `[!note]`；风险条目变 danger/warning 卡；顶部摘要 + 元信息卡 + 敏感度横幅 |
| §4 目录 | 正文 > 40 行或 ≥ 4 节自动生成，锚点去 emoji、链接带 `§N` |
| §5 表格 | 表头加粗、状态配 emoji、TSV 还原、列数不动 |
| §6 代码 | 补语言标识（扫全文猜）；**还原被复制丢掉的围栏**；连续命令行围栏成 bash |
| §8 视觉 | 分割线留白、`<details>` 原样、任务列表 GitHub 风格 |
| §11 遮盖 | 密码/口令/token/私钥/哈希 → `secret-toggle`（v1.4 写法）；**代码块内保留明文** |

### 6.3 排版三条铁律

1. **幂等**：排过一次再排一次，一字不差。所以「目录/元信息卡」这类派生块每次都拆掉重建；「摘要/相关」只有缺失时才补。
2. **不抢人的活**：用户手写的摘要卡、元信息卡（没有本站生成标记的）、相关区，一律保留原样。
3. **不因排版丢内容**：任何一步失败（AI 超时、解析失败）都退回规则版；正文一个字都不许吞。

### 6.4 保存即留痕 + 结构自愈（v1.9.1）

> [!warning] 保存会把「派生块」吃掉 —— 已修
> 编辑器里可能拿着一份**旧快照**（用户在我重新排版之前就打开了编辑）。
> 一保存，旧快照就把排版生成的「目录 / 相关 / 变更日志」整段覆盖没了 ——
> 用户看到的就是「变更日志不见了」。
>
> 现在保存链路会先做一次**结构自愈**（`ensure_derived`）：只补**缺的**派生块
> （元信息卡 / 目录 / 相关 / 变更日志），正文一个字不动，然后才记版本。
> 目录仍按长度门槛补，变更日志**每篇都补**（制度要求：每篇都能回答「谁改的、什么时候」）。


以前「变更日志」是排版时生成的一条静态记录，之后人在页面上改正文，它**不会变** ——
日志就成了谎话。现在的规矩写在保存链路上（`PUT /api/records/{id}`）：

| 场景 | 系统做什么 |
|---|---|
| 正文有改动 | `version` +0.1、`updated` 改今天、变更日志追加 **结构级描述**：`人工编辑 · 改「章节」：原文片段（+a/−b 行）`；新增/删除章节、改标题标签敏感度也会单独写出；元信息卡版本同步刷新 |
| 正文没变（只改分组/标签） | 什么都不做（不灌水版本号） |
| 重新排版 | **不升版本**（排版是机械变换，不是内容改动）；改动清单在预览弹窗里看 |
| 迁移 / 批量导入 | 用 `PUT /api/records/{id}?touch=0`，跳过版本与日志 |

> [!tip] 为什么排版不记版本
> 排版是幂等的：同一篇排两次结果一致。如果每次排版都 +0.1，版本号会变成噪音，
> 人也分不清「哪一版是真改过」。版本书只记**内容**的改动。

### 6.5 AI 的边界

- 只做「规则做不了」的三件事：**真 TL;DR、风险清单、目标/时间线抽取**。
- 默认**关**（当前模型一次 30–90 秒）；打开后结果按内容哈希缓存，40 秒超时自动退回规则版。
- AI 输出必须过 schema 校验（字段类型/长度/条数），不合规就当没有。
- AI 给的 `sensitivity` 只能**加严**不能降级（规则判 secret，模型说 confidential → 取 secret）。

## 8. 敏感信息与权限

### 8.1 敏感度分级（写死判定，不靠感觉）

| 级别 | 判定（规则版） | 表现 |
|---|---|---|
| `secret` | 出现凭证词（密码/口令/token/私钥/哈希…）**且** 有真实 IP/域名或攻击词（渗透/提权/getshell/越权…） | `> [!danger] 最高机密` + 元信息「敏感度 🔴 SECRET」 |
| `confidential` | 有凭证词，或客户/合同/金额/内部/身份证等 | `> [!warning] 内部资料` |
| `public` | 其余 | 无横幅 |

### 8.2 遮盖规范（§11）

```html
<span class="secret-toggle" tabindex="0">
  <span class="secret-mask">••••••</span>
  <span class="secret-value">明文</span>
</span>
```

- 遮罩固定点号（不泄露长度）；桌面悬停、移动端点按/键盘聚焦显示。
- 代码块里**不遮**（命令要能复制执行）；代码块里的旧遮盖标记会被还原成明文。
- 表格里「口令/密码/token」整列遮盖。
- 纯中文值不遮（「密码错误」不是凭证）。

### 8.3 权限与审计

- 权限两维：**页面位**（能否进「知识库」页）+ **模型位**（note 的 read/write）；AI 是**独立功能位**（`ai`），与笔记读写分开。
- 所有 `POST/PUT/PATCH/DELETE` 由中间件落审计（`GET /api/system/audit`），记录人、动作、资源、状态。
- 删除是**软删除**：进回收站，`POST /api/recycle/records/{id}/restore` 可恢复；物理清理由管理员在回收站执行。

## 9. 命名 / 去重 / 双链 / 标签

| 项 | 制度 |
|---|---|
| 命名 | 短、可检索、不含日期后缀（日期在 front-matter）；同一主题不建第二篇 |
| 去重 | 建之前 `GET /api/search?keyword=` 或 `GET /api/notes/extract`；同名笔记用「补充」而不是「新建」 |
| 双链 | `[[笔记标题]]`；保存后调 `POST /api/notes/{id}/sync-links` 重算；反链查 `GET /api/notes/{id}/backlinks` |
| 标签 | 3–6 个域标签（pentest / ops / api / database / frontend…），不用 `#` 前缀，不写色值/数字 |
| 分组 | 「标签式」归属：改分组只动 `data.group_id`，不复制笔记 |
| 相关 | `related` 列表 + 引号；由规则按标签/标题/正文打分（≥4 分）或人工指定 |

## 10. 硬约束（agent 必须遵守）

> 编号即规则号；出现违规在变更日志里写清原因与补救。

1. **先读后写**：写之前必须 `GET` 目标记录；已有内容不是自己写的，只能追加/补充，不能整段替换。
2. **不手拼 front-matter**：新建走 `POST /api/notes/template`（骨架）+ `POST /api/notes/format`；手拼必然漏字段、写坏 YAML。
3. **只补缺，不覆盖**：已有摘要卡 / 元信息卡 / 相关区（无本站生成标记的）一律保留。
4. **凭证必须遮盖**：正文与表格里的口令、token、私钥用 `secret-toggle`；代码块内保持明文并在敏感度上标 secret。
5. **敏感度不许降级**：`secret` 是上限判定，任何"看起来不要紧"的自我说服都不算理由。
6. **不直接改库**：所有写走 REST API；只读排查用容器内连接（`docker exec kb-backend`）。
7. **删除只走软删除**：`DELETE /api/records/{id}` → 回收站；不执行物理删除，不批量删。
8. **批量前出计划**：> 20 条先列出「目标 / 数量 / 影响面 / 回滚方式」，等人确认。
9. **幂等**：同一笔记重复排版结果一致；脚本重跑不产生重复章节、重复相关、重复变更行。
10. **验证必须实测**：说「已修复」必须附脚本名 + 断言数（如 `verify-note-format.py 134 项通过`），禁止凭感觉。
11. **不预生成配置**：不覆盖 `.env` / `.obsidian` / 用户已有设置；需要配置项时让用户在界面改，再读实际值。
12. **AI 可关**：调用 AI 的功能必须能退回规则版；超时/失败不得阻塞主流程，不得把模型输出直接当事实写库。
13. **不动结构**：不改实体模型、字段定义、权限、用户；那是管理员操作（`model_manage` 功能位）。
14. **变更要留痕**：正文改动由保存链路自动写（version +0.1 / updated / 变更日志行），不要手工伪造日志行；机械搬运（迁移/导入）用 `?touch=0` 跳过；代码改动在 `CHANGELOG.md` 记一节并升 `app_version`。

**违规判定**

| 行为 | 判定 | 处理 |
|---|---|---|
| 覆盖用户手写摘要/正文 | 越权 | 从备份/回收站恢复，变更日志记明 |
| 明文写入口令且未标 secret | 安全违规 | 立即遮盖 + 重排 + 记审计 |
| 直接 UPDATE kb.db | 越权 | 以备份为准回滚，排查是否丢索引 |
| 未跑验收就说"通过" | 失信 | 补跑并把结果贴进记录 |
| 批量删除 / 物理删除 | 严重越权 | 立即停止，走回收站恢复流程 |

## 11. 标准工作流

### 11.1 新建一篇笔记（agent）

```bash
# 0) 取 note 模型的 type_id 与当前会话
GET /api/entity-types            # 找 key=note
GET /api/auth/status

# 1) 出骨架（可选，推荐：渗透/排障/教程）
POST /api/notes/template
{ "title": "…", "profile": "pentest-record", "tags": ["pentest"] }

# 2) 排版（把散乱正文变成规范笔记；不落库，先看结果）
POST /api/notes/format
{ "content": "<散乱正文>", "title": "…", "tags": ["…"], "use_ai": false }

# 3) 建记录
POST /api/records/type/{note_type_id}
{ "data": { "title": "…", "content": "<格式化后的正文>", "tags": ["…"] } }

# 4) 重算双链
POST /api/notes/{id}/sync-links   { "content": "<正文>" }
```

### 11.2 修改已有笔记

```text
1. GET /api/records/{id}                        # 读现状，确认归属与结构
2. 只改要改的字段（title/tags/group_id 等）
3. 正文有变动 → PUT /api/records/{id}（整份 data 带上，别丢 parent/group_id）
4. 需要重排 → POST /api/notes/{id}/format（幂等；已规范会返回 changed:false）
5. 正文变了 → POST /api/notes/{id}/sync-links
6. 在「📝 变更日志」加一行：日期 / 版本 / 改了什么 / 来源
```

### 11.3 批量导入（> 20 篇）

```text
1. 先出计划表：来源 / 篇数 / 目标分组 / 命名规则 / 敏感度分布 / 回滚方式
2. 等人确认
3. 逐篇走 11.1 的 2–4 步（用脚本，串行；每 10 篇打印一次进度）
4. 抽 3 篇做要素体检（GET 记录 → element_audit 视角）
5. 汇总：成功/失败/跳过 三张清单，失败的全量重试或落盘
```

### 11.4 巡检（每周 / 发版前）

```bash
python3 scripts/verify-note-format.py        # 规则与幂等
KB_TOKEN=… python3 scripts/verify-note-autofmt-api.py   # 接口 + 落库
node scripts/kb-verify-note-autofmt.cjs      # 浏览器端到端
node scripts/kb-verify-note-editor.cjs       # 编辑器几何
cd frontend && npm test                      # 前端纯函数
docker run --rm -v "$PWD/backend":/app -w /app kb-workbench-backend:latest \
  python -m unittest discover -s tests -q    # 后端单测
```

### 11.5 迁移 / 回填

- 老笔记重排：`POST /api/notes/{id}/format`；先 `use_ai:false` 看规则版，再按需开 AI。
- 旧版排版产物（`## 代码块` 章节、TSV 表格、重复「相关」）会被自动还原/去重 —— 不需要手工改。
- 迁移前先 `./scripts/backup.sh`；迁移后抽查 10 篇的要素体检。

## 12. 验收标准（DoD）

一篇「合格笔记」的最低线：

- [ ] front-matter 合法（`yaml.safe_load` 通过），必填字段齐
- [ ] 标题 ≤ 40 字；H1 与 title 语义一致
- [ ] 有摘要（> 4 行或 ≥ 2 节时）与元信息卡
- [ ] 章节有编号；代码块有语言；表格表头加粗
- [ ] 凭证已遮盖；`sensitivity` 与内容匹配
- [ ] 有凭证/攻击细节的笔记：有最高机密/内部资料横幅
- [ ] 长笔记（> 15 行或 ≥ 5 节）有变更日志
- [ ] 重复排版 `changed:false`（幂等）

一次「合格交付」的最低线：

- [ ] 相关脚本全部通过，断言数写进记录
- [ ] `CHANGELOG.md` 有新一节，`app_version` 已升
- [ ] 影响用户数据的改动有备份与回滚说明
- [ ] 新增规则有对应断言（没有断言 = 没做）

## 13. 故障排查

| 症状 | 原因 | 处理 |
|---|---|---|
| 笔记打开是 `> [!abstract]` 一堆源码 | 前端未构建到新版 | `docker compose build frontend && docker compose up -d frontend` |
| 排版后 `changed:false` 但看着没变 | 内容已规范；变化在渲染层（缓存） | 强刷；确认前端镜像版本 `/api/health` |
| front-matter 属性面板空白 | YAML 非法（多半是 `related` 写法） | 用 `format` 重排；`related` 改成列表 + 引号 |
| 目录锚点跳不过去 | 标题里有 `()` `:` 等字符 | 锚点去标点属预期，必要时改标题 |
| 口令没遮住 | 不是「键 + 分隔 + 值」形态，或在代码块里 | 改成 `密码: xxx`；代码块内属预期明文 |
| AI 结构化一直不生效 | 未配置 AI / 超时 40s / 返回非法 JSON | 关掉 AI 用规则版；看 `/api/ai/config` |
| 双链断了 | 改了标题但没同步 | `POST /api/notes/{id}/sync-links` |
| 回收站里找不到删的笔记 | 管理员已物理清理 | 以备份为准恢复 |

## 14. 与 vault 手册的分工

| | vault（Obsidian） | 知识库（KB Workbench） |
|---|---|---|
| 通道 | MCP / 文件系统 | REST API / Web UI |
| 元数据 | front-matter（文件头） | front-matter 在 content 里 + 记录字段 |
| 检索 | Obsidian 搜索 / Dataview | FTS5 + 向量 + 业务查询 |
| 权限 | 文件系统 | 页面位 + 模型位 + 功能位 |
| 审计 | git 历史 | 审计表 + 变更日志 |
| 排版 | 人 + agent 手写 | **规则自动排版 + 要素体检**（本手册 §6/§7） |

> 两边共享同一套**排版规范**（`笔记UI排版规范` v1.7），所以同一篇内容在两边看起来应该一致；
> 不一致时以规范为准，先修排版器，不要手改笔记。
