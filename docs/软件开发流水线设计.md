# 软件开发流水线设计（v1.3.0 的实现契约）

> 这份文档是「后端流水线」与「前端工作台」两边共同遵守的契约。
> 接口名、字段名、状态机都以本文为准；实现细节各写各的，接口不许各改各的。

## 0. 这一版要解决什么

用户提的原话是三件事：

1. 「软件开发部分功能还需补全，目前达不到开发可用状态」
2. 「生成方案进度卡 50%」
3. 「页面排版和UI也有问题」

补充目标：「要体现专业级软件开发的能力，可以一站式理解需求、补全需求、
转化需求，形成可用的软件程序项目」。

### 0.1 先说清楚「为什么现在不可用」（已复现，别再猜）

| 现象 | 真实原因 | 证据 |
|---|---|---|
| 生成方案进度永远 50% | 后端 `GET /api/dev/jobs/{id}` 返回 `{"job": {...}}`，前端 `pollJob` 把**整个包装对象**塞进了 `job.value`，于是 `job.total` 永远是 `undefined` → `jobProgress` 走进「不知道总量」的兜底分支 → 固定 50%、文案固定「进行中」；作业早就 `failed` 了，页面永远不报 | 浏览器复现：连续 78s 显示 `50% 进行中`；DB 里作业 id=2 状态是 `failed`，错误「模型没有返回可解析的方案 JSON」 |
| 生成方案失败 | 模型输出被 `max_tokens=2048` 截断（`finish_reason: "length"`），JSON 不完整 → `parse_json_block` 解析不出来 | 直接调模型复现：`finish_reason=length`，正文 2048 字符处戛然而止 |
| 生成出来的东西不对 | 提示词没约束结构：模型把 `summary`/`architecture` 给成了**对象**（代码按字符串取），还把用户选的 Python/FastAPI 换成了 Java/Spring Boot | 同一次调用原文 |
| 整个模块不能用 | 默认「离线闭环」模式**不认**应用自己已经配好的云端大模型（MiniMax-M3.1-Flash），必须另配一个本地 OpenAI 兼容端点；没配 → 整个模块拒绝工作 | `/api/dev/doctor` → `model.ok=false`，`missing:["model_endpoint"]` |

结论：**不是「功能少」，是「链路断」**——
进度条断（前后端契约错）、模型调用断（截断）、结构断（无 schema）、可用性断（模型配置割裂）。
这一版要一次把这四条都接上，再往上加专业流水线。

## 1. 专业级流水线：四阶段

专业软件开发不是「一次调用出一段方案」，而是**四段有交付物、有验收标准、能被人工修订**的推进。

| # | 阶段 | key | 交付物 | 用户在做什么 | 能不能自动往下走 |
|---|---|---|---|---|---|
| 1 | 需求理解 | `clarify` | 需求理解摘要 + **澄清问题清单**（每题带候选项） | 回答澄清问题 | ❌ 必须人回答（这是「理解需求」） |
| 2 | 需求补全 | `specify` | **需求规格**：用户故事 + 验收标准、非功能需求、数据模型、边界与异常、明确不做的范围 | 审阅 / 改 | ⚠️ 可以自动跑，但默认先给人看 |
| 3 | 需求转化 | `design` | **设计**：架构、模块划分、数据表、接口清单、任务拆解（含依赖） | 审阅 / 改 | ⚠️ 同上 |
| 4 | 项目生成 | `implement` | **可运行的项目文件**：真实源码、配置、README、测试、启动脚本 | 验收 / 导出 ZIP | ✅ |

阶段之间**有闸门**：
`clarify` 没回答完 → 不许进 `specify`；`specify` 没产出 → 不许进 `design`。
闸门状态由后端算，前端只负责显示。

### 1.1 各阶段的输出结构（JSON，字段名不许改）

**clarify**（存 `pipeline.stages.clarify.data`）

```json
{
  "understanding": "一段话：这个系统给谁用、解决什么问题、边界在哪",
  "assumptions": ["我们默认……（写下来让用户去推翻）"],
  "questions": [
    {
      "id": "q1",
      "question": "工单从哪来？人工录入还是外部系统推送？",
      "why": "决定要不要做导入和幂等",
      "options": ["人工录入", "外部系统推送", "两者都要"],
      "allow_free": true
    }
  ]
}
```
`questions` 为空 = 模型认为需求已经够清楚（合法状态，要在界面上说清楚「无需澄清」）。

**specify**（存 `pipeline.stages.specify.data`）

```json
{
  "stories": [
    {"id": "S1", "title": "录入工单", "as_a": "客服",
     "i_want": "录入一条工单", "so_that": "能统计工作量",
     "acceptance": ["必填：标题、负责人、截止时间", "保存后列表可见"]}
  ],
  "nonfunctional": ["性能：列表查询 P95 < 500ms", "安全：仅内网可访问"],
  "data_model": [{"entity": "Ticket", "fields": ["id", "title", "owner", "due_at", "status"]}],
  "edge_cases": ["同一人名下多条工单", "跨月统计的边界"],
  "out_of_scope": ["工单审批流", "消息推送"]
}
```

**design**（存 `pipeline.stages.design.data`）

```json
{
  "architecture": "一段话讲清楚整体形态与关键取舍",
  "modules": [{"name": "tickets", "responsibility": "工单增删改查", "depends_on": []}],
  "data_tables": [{"name": "ticket", "columns": [{"name": "id", "type": "INTEGER"}]}],
  "apis": [{"method": "POST", "path": "/api/tickets", "purpose": "新建工单"}],
  "risks": ["导出百万行会占内存 → 改用流式写出"]
}
```
任务拆解**不放在 design.data 里** —— 它要落 `dev_task` 表（有依赖关系、要能逐个生成产出）。
`design` 阶段跑完时，服务端把任务写进 `dev_task`，`depends_on` 用真实 task id。

**implement**（不存 JSON，产物是 `dev_artifact` 行）
每个文件一行 `dev_artifact`：
`path` = 项目内相对路径（如 `backend/app/main.py`），
`filename` = 文件名，`content` = 全文，`language` = `python|javascript|markdown|dockerfile|...`，
`artifact_type` = `code|config|doc`，`source` = `model`。

必须包含（否则不算「可用的软件项目」）：
- `README.md` —— 怎么装、怎么跑、怎么测
- 依赖清单（`requirements.txt` / `package.json`）
- 至少一个可运行的入口文件
- 至少一个测试文件
- 启动脚本或 Dockerfile

## 2. 状态机

```
        ┌──────────┐  回答完澄清   ┌──────────┐  审阅通过   ┌──────────┐  生成完   ┌──────────┐
draft → │ clarify  │ ───────────→ │ specify  │ ──────────→ │  design  │ ───────→ │implement │
        │ 需求理解 │              │ 需求补全 │              │ 需求转化 │          │ 项目生成 │
        └──────────┘              └──────────┘              └──────────┘          └──────────┘
             │                           │                        │                     │
          needs_input ────────────────→（可重跑）              （可重跑）              → done
```

每个阶段的状态取值（前端按这五种渲染，不要自己发明）：
`pending`（没做）/ `running`（正在跑）/ `needs_input`（等用户输入）/
`done`（做完了）/ `failed`（失败了，`error` 里说原因）。

`pipeline.current_stage` = 第一个还没 `done` 的阶段。

## 3. 接口契约

前缀 `/api/dev`，鉴权与现有 dev 接口一致（`current_principal` + `_guard_perm`）。

### 3.1 读流水线
```
GET /api/dev/projects/{id}/pipeline
→ {
    "pipeline": { "current_stage": "clarify",
                  "stages": { "clarify": {"status":"done","at":"...","data":{...},"answers":{...},"error":""}, ... } },
    "stages": [ {"key":"clarify","title":"需求理解","status":"done","summary":"一句人话","blocking":false} ],
    "gates": { "can_specify": true, "can_design": false, "can_implement": false }
  }
```
`stages[]` 是给左栏导航用的精简视图（顺序固定：clarify → specify → design → implement）。

### 3.2 跑某个阶段
```
POST /api/dev/projects/{id}/stages/{stage}/run     body: {"extra": "", "force": false}
→ { "job": {...} }        # 后台作业，前端轮询 /api/dev/jobs/{id}
```
- `stage` ∈ `clarify|specify|design|implement`。
- **闸门不通过 → 直接返回 409 与原因**，不要先跑再失败：
  `{ok:false, detail:"需求理解还没完成，先回答澄清问题", missing:["clarify"], how_to_fix:["...在需求理解阶段回答问题"]}`
- `force=true` 时允许重跑已完成阶段（覆盖旧产出）。

### 3.3 提交澄清答案 / 编辑阶段产出
```
POST /api/dev/projects/{id}/stages/{stage}/answer   body: {"answers": {"q1": "人工录入"}, "notes": ""}
→ { "pipeline": {...} }
```
`clarify` 用 `answers`；`specify`/`design` 用 `notes` + 覆盖 `data`（可选）。

### 3.4 导出可运行项目
```
GET /api/dev/projects/{id}/export.zip
→ application/zip，Content-Disposition: attachment; filename="<项目名>-v<版本>.zip"
```
ZIP 里必须有一层顶层目录（项目名），内含 `README.md` 与全部 `dev_artifact` 文件。
**没有 implement 产出时返回 409**，并说清「先跑项目生成」。

### 3.5 作业进度（沿用 dna_job，但语义要改）
```
GET /api/dev/jobs/{id} → { "job": { id, job_type, status, total, processed, current, error, detail, ... } }
```
- `job_type` = `dev_stage`
- `total` = **该阶段的真实步骤数**（不是 1，也不是 0）
- `processed` = 已完成的步骤数，**每步完成就写回**
- `current` = 当前步骤的人话（如「调用模型生成需求规格」「校验结构」）
- `status` ∈ `pending|running|done|failed`

## 3.6 推理模型的坑（**最重要的一条，后端已经踩过**）

实测 MiniMax-M3.1-Flash，`max_tokens=2048` 时：

```
completion_tokens              = 2048
completion_tokens_details.reasoning_tokens = 2049
正文长度                       = 0        ← 一个字都没有
finish_reason                  = length
```

**模型把整个输出预算花在思考块上，正文一个字都没吐出来。**
所以「JSON 写了一半」「解析不出来」这些解释都不对 ——
它压根没开始写正文。加大预算之前，重试一万次也都是空的。

`backend/app/services/dev.py` 的 `call_model` 现在会：
`finish_reason=length` 或正文为空 → `max_tokens` 翻倍重试，
直到写完或摸到天花板（云端模型的天花板是用户在 AI 设置里定的
`max_tokens_ceiling`，不能替他超）。实测 2048 → 4096 就正常了。

**写阶段提示词时也要记住**：别指望一次调用就够，
`implement` 阶段要吐一整套项目文件，预算要留够。

## 4. 前后端约定（别再踩这几个坑）

1. **包装对象**：所有返回 `{job: ...}` 的接口，前端必须取 `.job`。
   后端**不要**改成直接返回 job —— 保持 `{job:...}`，前端统一解包。
   → 前端要写一个 `unwrapJob(r)` 兜底：`r?.job || r`。
2. **进度条不许有假的百分比**：`total` 未知时**不许**显示 50%，
   显示「进行中…」并用不确定态；`total` 已知时必须按 `processed/total` 算。
3. **作业失败必须让用户看见**：`failed` 时显示 `error` + `how_to_fix`，不能只显示「进行中」。
4. **模型调用的 max_tokens 要够**：dev 模块专用，默认 **8192**（在 `dev_config` 里可配）。
   解析失败要能重试一次（提示模型精简），并支持**截断 JSON 的抢救**（补括号）。
5. **提示词必须带 schema**：明确「只输出 JSON」「summary/architecture 是字符串」
   「不要改动用户指定的技术栈」「tasks 是数组，每项有 title/description/acceptance/depends_on」。
6. **模式不能把功能锁死**：离线模式没有本地模型时，
   后端在 `doctor` 里要明确给出「系统大模型已就绪，可切到在线协同」；
   前端给一个**一键切模式并重跑**的按钮。
